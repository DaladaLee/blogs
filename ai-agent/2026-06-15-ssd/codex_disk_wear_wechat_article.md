# Codex （是个好人）正在加速用户的 SSD 报废

这几天我遇到一个很离谱的问题：电脑主盘每秒持续写入一百多 MB。不是那种几秒钟的尖峰，是一直写。

我一开始以为是 Docker、索引、浏览器缓存，或者哪个服务抽风了。查到最后，主要来自 Codex 的本地 SQLite 日志。简单说就是：它一直写日志，又一直清日志。所以文件看起来不一定越来越大，但硬盘写入已经实打实发生了。

我这台机器开机 21 天，主盘累计写入大约 **37 TB**。

> 按这个速度跑一年，就是大约 **640 TB** 写入。虽然主盘是 4TB，但对一块 1 TB SSD 来说，相当于一年写满整盘 640 次。有些消费级 1 TB SSD 的标称寿命也就 600 TBW 左右。也就是说，如果一块 1 TB SSD 累计写入约 600 TB 数据，就已经接近厂商标称的耐久上限，不一定立刻损坏，但风险和不可控性会明显上升。

看到这个数字的时候，我真的现在 SSD 涨价跟 OpenAi 的关系又多了一条。OpenAi 正在加速 codex 用户的 SSD 报废。
现在硬盘也不便宜。用 AI 来就已经在付 token 钱了，结果现在发现，本地 Agent 还可能在背后刷我的 SSD。这就很难绷。

云端账单至少你每个月能看到，硬盘寿命这东西，它不会每天跳出来跟你说“兄弟我今天又被写了 1TB”。等你发现的时候，磁盘估计快报废了。

## 最危险的是你不一定能看出来

很多人排查磁盘问题，第一反应是看哪个文件最大。但这次的问题不在于文件最后有多大，而在于它写得有多勤。

我本地最关键的文件是：

```text
~/.codex/logs_2.sqlite
~/.codex/logs_2.sqlite-wal
```

15 秒采样里，数据库保留行数几乎没变，但内部 row id 增加了约 **36,211**。换句话说，它在很短时间里插入了大量日志，又通过保留策略清掉一部分。

所以你可能会看到：文件大小没怎么涨，磁盘却一直在写。这也是我一开始很困惑的地方：看容量，好像没那么夸张；看实时 IO，人直接傻了。

---

## 如果你重度用 Codex，建议现在就看一眼

尤其是你长期跑 Codex CLI、app-server、多会话、多 Agent 的话，真的建议看一下。

先看 Codex 目录：

```bash
ls -lh ~/.codex | grep sqlite
```

重点看：

```text
logs_2.sqlite
logs_2.sqlite-wal
```

再看实时磁盘写入：

```bash
iostat -dx 1
```

如果你想定位具体进程：

```bash
pidstat -d 1
lsof | grep '.codex/.*sqlite'
```

如果你看到 `logs_2.sqlite-wal` 一直在高频写，别只看它现在多大。重点是它每秒写多少，写了多久。

## 我已经提到社区了

我把这次的数据整理到了 Codex issue，也推了一个最小修复分支，希望 codex 能尽快修复吧。诉求也很简单：日志可以有，但别默认这么刷用户硬盘。

尤其是 AI Agent 这种东西，它不是你手动点一下就结束。它会长期跑，会开很多进程，会自动做很多事。这种工具的后台写入，真的应该更克制。

以前我们说 AI 成本，主要想到 API 账单、GPU、服务器。现在我发现，本地 Agent 还会消耗你自己的电脑：CPU、内存、风扇、电池，还有 SSD 寿命。这事挺离谱的。

如果你是 Codex 深度用户，今天就看一眼 `~/.codex`。别等 SSD 先替你报警。
